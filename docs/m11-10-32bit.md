# ⑩ 32 位覆盖 —— 诚实声明 + 装机守卫

## 事实：**恰好三样东西与架构绑定**

| 产物 | 架构 | 用途 |
|---|---|---|
| `bin/uperf` | **aarch64 ELF**（`file` 实测） | 守护进程本体 |
| `bin/busybox/busybox` | **aarch64，静态链接** | 模块自带的 busybox |
| `bin/libsfanalysis_rs.so` | **aarch64 cdylib** | 注入 `surfaceflinger` |

其余全是 shell 或 dex（`ForegroundHelper` 的 dex 与架构无关），**架构中立**。

## 改前的行为（不诚实的地方）

`customize.sh` **没有任何 ABI 检查**，而 `libsysinfo.sh` 里的 `is_aarch64()` 是**死代码**
（定义了，全仓无调用）。于是一个 32 位设备装上模块会：安装"成功" → 开机 `exec` 失败
（ENOEXEC）→ 什么都不工作，且日志里没有一句解释。

## 改后

* `libsysinfo.sh`：`module_abi()` / `abi_supported()` / `is_aarch64()`（终于被用上），
  加上 `require_aarch64()` —— 不支持时把**原因逐条打出来**并返回非零。
* `setup.sh`：装机前先 `require_aarch64 || abort`（`customize.sh` 对 setup.sh 的非零退出
  本来就会 `abort`），所以**装机阶段就拒绝**，而不是留到开机静默失败。
* `webui.sh status`：新增 `device.abi` 与 `module.arch_supported`；WebUI 设备卡加一行
  「指令集 / ABI」，不支持时显示 `(unsupported / 不支持)`。
* 测试缝：`UPERF_FAKE_ABI`（与 `UPERF_FAKE_ROOT` 同思路）让拒绝路径能在 64 位设备上复现。

## 为什么**没有**补 32 位构建（[U]，说清楚而不是含糊）

本仓确实**不提供** 32 位产物。要做全，至少需要：

1. **busybox**：模块里那份是别人编译好的 aarch64 静态二进制，本仓无法从这里重建 32 位版；
2. **`libsfanalysis_rs.so`**：32 位设备上 `surfaceflinger` 本身是 32 位，得再出一份
   armv7 cdylib，并按架构分目录；
3. **`bin/` 布局 + 脚本**：改成 `bin/<abi>/…`，`libuperf.sh`/`setup.sh` 按 ABI 选路；
4. **构建**：NDK 的 `armv7a-linux-androideabi` 工具链 + cargo `armv7-linux-androideabi`
   target + cmake toolchain + `build.sh check` 的两份产物断言。

这是一整块工作，且**没有任何 32 位设备可以验证**（手上两台都是 arm64）。按本仓"判据不足
就写 [U]、不臆造"的规矩：**不做的原因写在这里，而不是假装做了。**

## 真机现实（alioth）

`ro.product.cpu.abilist = arm64-v8a,armeabi-v7a,armeabi` —— 这是一台**混合**设备：
32 位应用跑得起来，但守护进程与 `surfaceflinger` 都是 64 位，所以 arm64 产物在这里完全够用。
守卫要挡的是"**只支持 32 位**"的设备，不是这种混合设备。

## 验证

[V] 真机（`scripts/m11-abi-check.sh`）：真实 ABI 下 `module_abi=arm64-v8a`、
`abi_supported=1`、`require_aarch64` 返回 0；`UPERF_FAKE_ABI=armeabi-v7a` 下逐条打出原因并
返回非零（装机即被 `abort`）。`webui.sh status` 输出 `device.abi=arm64-v8a`、
`module.arch_supported=1`。

[U] 没有 32 位设备，所以"守卫在真 32 位机上会挡住装机"只有**代码路径 + 假 ABI**的证据，
没有真机证据 —— 如实记在这里。
